# DB SSOT + Google Drive 동기화 + Docker 전환 가이드

이 문서는 `new_stock_crawler`를 "Parquet 파일이 SSOT"에서 "SQLite DB가 SSOT" 구조로, 그리고
로컬 실행에서 Docker 컨테이너 내장 cron 실행으로 전환하면서 겪은 문제와 그 해결 이유를
정리한 것입니다. `krx-auto-crawling`의 동일 계열 마이그레이션 가이드를 참고해 같은 형식으로
작성했습니다. 다른 크론잡을 같은 형태(DB SSOT + Docker)로 옮길 때 이 문서의 체크리스트를
먼저 훑고 시작하세요.

---

## 1. 배경 — 왜 바꿨는가

기존 구조는 `output/parquet/{연도}.parquet`가 SSOT였고, 상장 종목의 OHLC 가격은 크롤링 도중
즉석으로("오늘 상장이면 15:30 이후에만", "과거 상장이면 무조건 1회") 시도한 뒤 실패하면
재시도 없이 넘어가는 구조였습니다. 문제는:

- **가격 조회 시점이 잘못되면(장마감 직후라 KRX가 아직 데이터를 안 준 경우) 영구 누락** —
  재시도 로직이 없어 다음 크롤링에서도 다시 채워지지 않음. 실제로 상장일 2026.06.30인
  종목의 시가/종가가 계속 비어있던 사례를 발견 (원인 규명 후 해결 — 2.2절 참고).
- `(종목명, 상장일)` 복합키 upsert라 **상장일이 정정되면(연기 등) 같은 종목이 다른 행으로
  중복 적재될 위험**이 있었음.
- Parquet는 파일 하나를 통째로 읽고 통째로 다시 씀 — SQLite로 바꾸면 향후 조건부 조회
  (예: 특정 상장일 이후만 조회)가 SQL로 가능해짐.

그래서 **SQLite(연도별 분리 파일 `db/{연도}.db`)를 SSOT로 두고, 가격 백필은 크롤링과
분리된 별도 단계에서 "DB 상태를 직접 조회해 아직 못 채운 행만" 처리하는 방식**으로
바꿨습니다.

## 2. 실제로 발생했던 문제와 원인

### 2.1 PK 설계 — 복합키 → 종목명 단일키

`(종목명, 상장일)` 복합키를 유지한 채 SQLite로 옮기면 상장일 정정 시나리오에서 여전히
중복 적재가 가능했습니다. **`상장일`을 PK에서 빼고 종목명 단일키**로 단순화(동명 재상장
케이스는 덮어써짐 — 이 도구 목적상 허용). `SqliteRepository.save()`는 `종목명` 기준
`drop_duplicates(keep="last")`로 upsert하고, `CREATE UNIQUE INDEX`로 안전장치를 둡니다.

**교훈:** 시계열/이력성 필드(상장일처럼 정정 가능한 값)를 PK에 포함하면, "값이 바뀌는
이벤트"가 "새 레코드 생성"으로 오인됩니다. PK는 정정 불가능한 식별자만으로 구성할 것.

### 2.2 "완료 여부" 판단 로직이 두 군데로 흩어져 있었음

옛 코드는 `CrawlerService.run_scheduled()`가 크롤링 도중 즉석으로 가격을 시도(오늘 상장이면
15:30 게이트, 과거 상장이면 무조건 1회, 실패해도 재시도 없음)했고, 별도로
`EnrichmentService.enrich_data()`는 수동 `enrich` 커맨드로 **전체 데이터를 무조건 재조회**
(이미 값 있는 행도 매번 다시 API 호출)했습니다. 두 경로의 판단 기준이 서로 달랐습니다.

`crawler_service.py`의 즉석 enrichment를 완전히 제거하고, **"수집 → 저장" 이후 DB 상태를
직접 스캔해서 아직 못 채운 행만 채우는 단일 백필 단계**로 통일했습니다
(`EnrichmentService.enrich_data`):

1. **이미 채워진 행 스킵**: `pd.notna(row.get("종가"))`면 API 재호출 없이 건너뜀 — 재실행이
   안전(idempotent)해짐.
2. **상장일 컷오프 스킵**: 상장일 15:50(장마감 후 KRX 시세 확정 대기 버퍼)이 아직 안
   지났으면 건너뜀. 다음 실행에서 자동으로 재시도됨 — "실패하면 끝"이 아니라 "아직
   때가 안 됐으면 다음 번에"로 바뀜.

`full`/`daily` 커맨드는 크롤링 직후 이 백필 단계를 자동 호출하고, 수동 `enrich` 커맨드는
동일 로직을 전체 DB 대상으로 재사용합니다 — 판단 기준이 완전히 하나로 통일됨.

**교훈:** "완료 여부" 판단 로직은 반드시 **DB를 직접 조회하는 단일 함수/서비스**로 통일하고,
자동 경로와 수동 경로가 같은 함수를 쓰게 만들 것. 시점(장마감 전/후) 판단이 필요한
도메인이면, "실패 시 포기"가 아니라 "조건이 안 맞으면 다음 실행에서 자동 재시도"로 설계할 것.

### 2.3 NaN 종목명이 스킵 조건을 통과하던 버그

`if not stock_name:`로 결측 종목명을 걸러내려 했는데, pandas가 결측 종목명을 `NaN`(float)로
로드하면 `bool(nan)`이 `True`라 이 조건을 통과했습니다. 조용히 넘어가던 게 아니라 그 다음
문자열 처리 단계에서 예외가 나고 넓은 `except Exception`에 삼켜져 "[SKIP]" 대신
"[ERROR]" 로그만 매번 찍혔습니다. `if pd.isna(stock_name) or not stock_name:`로 수정.

**교훈:** pandas DataFrame에서 온 값의 결측 체크는 `not x`가 아니라 `pd.isna(x)`(또는 둘 다)를
써야 함 — `bool(float('nan'))`은 `True`.

### 2.4 어댑터가 예외를 raise하는 설계 때문에 실제로 발생한 사고

Google Drive 연동(`GoogleDriveAdapter`)이 실패 시 예외를 그대로 raise하는 구조였고, 모든
호출부가 매번 `try/except`를 직접 감싸야 했습니다. Drive 동기화 유틸(`drive_sync.py`)에
새 호출(`get_or_create_subfolder("db")`)을 추가하면서 **이 한 곳만 try/except를
빠뜨렸고**, Drive 인증이 실패하면 크롤링과 가격 백필이 이미 성공했음에도 전체 커맨드가
예외로 실패 처리되는 버그가 실제로 발생했습니다(코드 리뷰 중 발견).

`krx-auto-crawling`의 `StoragePort`(모든 메서드가 `bool`/`Optional[...]`을 반환하고 어댑터
내부에서 예외를 직접 삼키는 계약)와 비교 검토한 뒤, 우리 `StoragePort`도 같은 방식으로
재설계했습니다: `upload_file() -> Optional[str]`, `list_files() -> list`(실패 시 빈 리스트),
`download_file() -> bool`. 호출자 실수(로컬 파일 없음)만 여전히 예외로 raise.

이 리팩터링 과정에서 **회귀를 하나 더 발견**했습니다: `auth.py`/`health.py`의 "Drive 연결
테스트"는 `list_files()`가 실패 시 raise하는 동작에 의존하고 있었는데, 반환값 기반으로
바꾸면 인증 실패가 "연결 확인됨(0개)"로 오탐될 뻔했습니다. 실패를 명확히 알아야 하는
호출자를 위해 `ensure_authenticated()`(실패 시 그대로 raise)를 별도로 노출해 해결.

**교훈:** "실패를 삼키고 안전한 값을 반환"하는 계약으로 인터페이스를 바꿀 때는, **그
실패 신호에 실제로 의존하고 있는 다른 호출부가 있는지 전수 조사**할 것 (`grep`으로
해당 메서드의 모든 호출부 확인). 헬스체크/연결테스트처럼 "실패 자체가 목적"인 호출은
예외 삼키기 계약에서 예외로 취급해야 함.

### 2.5 리팩터링 중 추가한 테스트가 실제로는 실행되지 않고 있었음

Google Drive 서브폴더 기능 추가 시 작성한 테스트 2개(`testget_or_create_subfolder_...`)가
`test` 뒤에 언더스코어를 빠뜨린 오타 때문에 pytest의 `python_functions = ["test_*"]` 패턴에
안 걸려 **한 번도 수집/실행되지 않고 있었습니다**. `--collect-only`로 실제 수집된 테스트
개수를 세어보다가 발견. 이름을 바로잡아 실제로 돌아가게 수정.

**교훈:** 테스트를 추가한 직후엔 `pytest -v --collect-only`(또는 실패를 일부러 주입해서
빨간불이 뜨는지)로 **그 테스트가 진짜로 수집/실행되는지 한 번은 직접 확인**할 것.
"통과했다"는 메시지만 보고 넘어가면 이런 오타가 영원히 안 잡힘.

### 2.6 참고 프로젝트 패턴을 검증 없이 그대로 복사했다가 배포 중 발견한 문제

`krx-auto-crawling`의 `cron-entrypoint.sh`(env를 파일로 덤프한 뒤 cron 잡에서 다시
로드하는 패턴 — 그 프로젝트는 config가 OS 환경변수 주입에 의존하기 때문에 필요)를 그대로
복사해 왔는데, 실제로 컨테이너를 띄워 검증하는 과정에서 덤프된 env 파일에
`KRX_USERNAME`/`GOOGLE_DRIVE_FOLDER_ID`가 전혀 없다는 걸 발견했습니다. 원인은 이
프로젝트의 `config.py`가 `pydantic-settings`로 `/app/.env` 파일을 **직접** 읽어들이는
방식이라(OS 환경변수 주입 여부와 무관), cron 잡이 애초에 환경변수를 상속받을 필요가
없었던 것. 불필요한 코드를 제거.

**교훈:** 다른 프로젝트의 인프라 패턴(특히 "왜 이게 필요한지"가 코드만 봐서는 안 드러나는
워크어라운드)을 가져올 때는, **그 워크어라운드가 전제하는 조건이 우리 프로젝트에도
실제로 성립하는지** 반드시 확인할 것. 실제 배포 환경에서 한 번 실행해보고 검증하는 게
가장 빠른 확인 방법.

## 3. Docker 전환 시 문제와 원인

### 3.1 `print()`가 Docker 로그 순서를 뒤섞을 위험

`krx-auto-crawling`이 겪었던 문제(비-TTY 환경에서 `print()`의 내부 버퍼링과 `logging`의
별도 flush 타이밍이 어긋나 로그 순서가 실제 실행 순서와 다르게 보일 수 있음 — "중복
실행"으로 오인하기 쉬움)를 미리 반영해, Docker 전환 전에 `src/` 전체에서 남아있던
`print()` 19곳(파싱 전략/파서, `PlaywrightPageProvider`, `GoogleDriveAdapter`)을
`logger.info/warning/error`로 일괄 교체했습니다. `auth.py`의 Rich `console.print`는
사람과의 대화형 상호작용이 목적이라 대상에서 제외.

### 3.2 Windows 체크아웃 시 셸 스크립트가 CRLF로 깨질 위험

`docker/*.sh`, `docker/crontab`, `Dockerfile`을 새로 추가하면서 `git add` 시 "LF will be
replaced by CRLF" 경고를 확인했습니다. Windows에서 `core.autocrlf`가 켜져 있으면 다음
체크아웃 때 이 파일들이 CRLF로 변환되고, 리눅스 컨테이너 안에서 `#!/bin/sh\r`로 shebang이
깨져 `bad interpreter` 오류가 날 수 있습니다. `.gitattributes`에
`docker/*.sh text eol=lf`, `docker/crontab text eol=lf`, `Dockerfile text eol=lf`를
추가해 항상 LF로 체크아웃되도록 강제.

**교훈:** Windows에서 작업하며 리눅스 컨테이너에 직접 복사되는 셸 스크립트를 추가할
때는 `.gitattributes`로 줄바꿈을 강제할 것 — 로컬에서 빌드가 잘 됐다고 안심하면 안 됨
(로컬 워킹 디렉터리의 파일은 이미 LF일 수 있어도, 재체크아웃 시 깨질 수 있음).

### 3.3 cron 데몬 기동에 root 권한 필요 (krx와 동일 이유)

`krx-auto-crawling`과 동일하게, 컨테이너를 non-root(`nonroot`)로 돌리면 cron 데몬 기동과
`/proc/1/fd/1`(컨테이너 stdout) 리다이렉션에 필요한 권한이 없어 스케줄된 잡이 아예 실행되지
않습니다. `docker-compose.yml`에서 **`crawler-cron` 서비스만** `user: root`로 오버라이드
(1회성 실행용 `crawler` 서비스는 기본 `nonroot` 유지).

### 3.4 실제 배포로 검증

`docker build` → `docker run`으로 이미지 빌드/CLI 동작을 먼저 확인하고, `docker compose up
-d crawler-cron`으로 실제 배포한 뒤:

- `docker exec ... ps aux | grep cron` — `cron -f`가 PID 1로 떠 있는지
- `docker exec ... cat /etc/cron.d/crawler-cron` — crontab 내용/권한(0644)이 맞는지
- `docker exec ... sh -c "cd /app && uv run python -c 'from config import config; ...'"` —
  `.env`가 실제로 로드되는지 (2.6절 문제를 이 단계에서 발견)

**교훈:** Docker 관련 변경은 로컬 `uv run` 테스트가 전부 통과해도 안심할 수 없음 —
**실제로 이미지를 빌드하고 컨테이너를 띄워서** 볼륨 마운트, 권한, 환경변수 로딩을 확인할
것.

## 4. 다른 크론잡을 같은 구조로 옮길 때 체크리스트

1. **PK에 정정 가능한 필드가 없는지 확인**: 시계열/이력 필드를 PK에 포함하면 정정 시
   중복 적재됨. 불변 식별자만으로 PK 구성.
2. **완료 판단 로직 단일화**: "이미 처리됨" 판단은 DB를 직접 조회하는 함수 하나로
   통일하고, 자동/수동 호출부가 같은 함수를 쓰게 만들 것. 시점 의존 로직이면 "실패=포기"가
   아니라 "다음 실행에서 자동 재시도"로 설계.
3. **pandas 결측치 체크는 `pd.isna()`**: `not x`만으로는 `NaN` float를 못 거름.
4. **어댑터의 실패 반환 계약을 통일**: 예외 raise 방식이면 모든 호출부가 try/except를
   빠뜨리지 않아야 하는 부담이 생김. 가능하면 어댑터 내부에서 실패를 삼키고
   `Optional`/`bool`/빈 컬렉션으로 반환하는 계약을 쓰되, 실패 자체가 신호여야 하는
   호출부(헬스체크 등)는 별도 메서드로 분리.
5. **인터페이스 계약을 바꿀 때는 실패 신호에 의존하는 다른 호출부를 전수 조사**:
   `grep`으로 해당 메서드의 모든 호출부를 확인하고, 그 신호에 의존하는 로직이 있는지 검토.
6. **신규 테스트는 수집/실행되는지 직접 확인**: `pytest --collect-only`로 이름 패턴이
   맞는지 확인하거나, 일부러 실패시켜 빨간불을 봐야 함.
7. **다른 프로젝트의 인프라 패턴을 가져올 때는 전제 조건을 검증**: 그 워크어라운드가
   왜 필요했는지 이해하고, 우리 프로젝트에도 같은 전제가 성립하는지 확인.
8. **`print()` 전량 제거**: Docker(비-TTY)로 옮기기 전에 로깅으로 통일.
9. **`.gitattributes`로 셸 스크립트 줄바꿈 강제**: Windows에서 작업하는 경우 특히 중요.
10. **cron 컨테이너 권한 확인**: non-root로 스케줄러 자체가 동작하는지 먼저 확인. 안 되면
    해당 서비스만 root로 오버라이드하고 나머지는 nonroot 유지.
11. **실제 이미지를 빌드/기동해서 검증**: 볼륨, 권한, 환경변수 로딩 방식(파일 직접 읽기
    vs OS 환경변수 주입)이 로컬 실행과 다를 수 있음.

## 5. 오케스트레이션 레이어 정리 (부록)

DB SSOT 전환과 별개로, CLI 커맨드(`full_crawl.py`/`daily_update.py`) 안에 "수집 → 백필 →
변경 연도 계산" 로직이 그대로 나열돼 있어 순환복잡도가 높고(radon 기준 C등급) 유닛테스트도
어려웠습니다. `krx-auto-crawling`의 `DailyRoutineService`(오케스트레이션 로직을
`core/services`의 별도 서비스로 분리하고 CLI는 그 서비스를 호출만 하는 얇은 어댑터로 두는
패턴)를 참고해 `CrawlOrchestratorService`를 신설했습니다.

krx의 `execute()`는 `None`을 반환하고 서비스 내부에서 로깅까지 처리하는데, 우리는
`CrawlRunResult(collected_count, changed_years)` 값 객체를 반환하도록 설계했습니다 —
오케스트레이터는 순수 로직(호출 순서 조합)만 책임지고, 로그 문구는 CLI가 결정합니다.
`run_daily`의 "1월이면 전년도까지 백필" 판단 기준일도 `today` 파라미터로 주입 가능하게
해서, 실제로 1월이 아니어도 그 경계 로직을 유닛테스트할 수 있게 했습니다.

결과: `full_crawl()` C→A(5), `daily_update()` C→B(8) (radon cc 기준). 오케스트레이터
자체는 mock 기반 TDD로 호출 순서/changed_years 병합/1월 경계 케이스를 테스트.

**교훈:** 참고 프로젝트의 패턴을 그대로 베끼기보다, "왜 이 구조인가"를 이해한 뒤 우리
상황에 맞게 개선할 부분(로깅과 로직의 분리, 시간 의존 로직의 테스트 가능성)을 찾아
반영할 것.

## 6. 아직 다루지 않은 것 (의도적으로 미룬 항목)

- **GitHub Actions 등 외부 트리거 경로**: `daily_update.py`가 한때 "GitHub Actions용"으로
  설계됐었지만, 최종적으로는 krx와 동일하게 컨테이너 내장 cron으로 자체 호스팅하는
  방식을 채택. 외부 스케줄러 연동은 미검증/미착수.
- **Google Drive 동시 쓰기에 대한 파일 락**: 지금은 순차 실행이라 불필요, 병렬 실행 잡이
  생기면 재검토 (krx와 동일한 판단).
- **여러 크론잡의 실행 결과를 한곳에 모아 알림으로 전달하는 오케스트레이션**: 별도 논의
  필요, healthchecks.io류 cron 모니터링 서비스에 잡별 ping을 붙이는 방식을 권장.
- **`export_excel.py`/`enrich_data.py` 등 CLI 커맨드 함수 자체의 유닛테스트**: 오케스트레이션
  로직은 `CrawlOrchestratorService`로 분리해 테스트 가능해졌지만, typer 커맨드 함수
  자체(인자 파싱, 옵션 조합)는 여전히 테스트가 없음.
