# DB SSOT + Google Drive 동기화 + Docker 전환 가이드

이 문서는 `new_stock_crawler`를 "Parquet 파일이 SSOT"에서 "SQLite DB가 SSOT" 구조로, 그리고
로컬 실행에서 Docker 컨테이너 내장 cron 실행으로 전환하면서 겪은 문제와 그 해결 이유를
정리한 것입니다. `krx-auto-crawling`의 동일 계열 마이그레이션 가이드를 참고해 같은 형식으로
작성했습니다. 다른 크론잡을 같은 형태(DB SSOT + Docker)로 옮길 때 이 문서의 체크리스트를
먼저 훑고 시작하세요.

---

## 1. 배경 — 왜 바꿨는가

기존 구조는 `output/parquet/{연도}.parquet`가 SSOT였고, 상장 종목의 OHLC 가격은 크롤링 도중
즉석으로("오늘 상장이면 15:30 이후에만", "과거 상장이면 무조건 1회") 시도한 뒤 실패하면
재시도 없이 넘어가는 구조였습니다. 문제는:

- **가격 조회 시점이 잘못되면(장마감 직후라 KRX가 아직 데이터를 안 준 경우) 영구 누락** —
  재시도 로직이 없어 다음 크롤링에서도 다시 채워지지 않음. 실제로 상장일 2026.06.30인
  종목의 시가/종가가 계속 비어있던 사례를 발견 (원인 규명 후 해결 — 2.2절 참고).
- `(종목명, 상장일)` 복합키 upsert라 **상장일이 정정되면(연기 등) 같은 종목이 다른 행으로
  중복 적재될 위험**이 있었음.
- Parquet는 파일 하나를 통째로 읽고 통째로 다시 씀 — SQLite로 바꾸면 향후 조건부 조회
  (예: 특정 상장일 이후만 조회)가 SQL로 가능해짐.

그래서 **SQLite(연도별 분리 파일 `db/{연도}.db`)를 SSOT로 두고, 가격 백필은 크롤링과
분리된 별도 단계에서 "DB 상태를 직접 조회해 아직 못 채운 행만" 처리하는 방식**으로
바꿨습니다.

## 2. 실제로 발생했던 문제와 원인

### 2.1 PK 설계 — 복합키 → 종목명 단일키

`(종목명, 상장일)` 복합키를 유지한 채 SQLite로 옮기면 상장일 정정 시나리오에서 여전히
중복 적재가 가능했습니다. **`상장일`을 PK에서 빼고 종목명 단일키**로 단순화(동명 재상장
케이스는 덮어써짐 — 이 도구 목적상 허용). `SqliteRepository.save()`는 `종목명` 기준
`drop_duplicates(keep="last")`로 upsert하고, `CREATE UNIQUE INDEX`로 안전장치를 둡니다.

**교훈:** 시계열/이력성 필드(상장일처럼 정정 가능한 값)를 PK에 포함하면, "값이 바뀌는
이벤트"가 "새 레코드 생성"으로 오인됩니다. PK는 정정 불가능한 식별자만으로 구성할 것.

### 2.2 "완료 여부" 판단 로직이 두 군데로 흩어져 있었음

옛 코드는 `CrawlerService.run_scheduled()`가 크롤링 도중 즉석으로 가격을 시도(오늘 상장이면
15:30 게이트, 과거 상장이면 무조건 1회, 실패해도 재시도 없음)했고, 별도로
`EnrichmentService.enrich_data()`는 수동 `enrich` 커맨드로 **전체 데이터를 무조건 재조회**
(이미 값 있는 행도 매번 다시 API 호출)했습니다. 두 경로의 판단 기준이 서로 달랐습니다.

`crawler_service.py`의 즉석 enrichment를 완전히 제거하고, **"수집 → 저장" 이후 DB 상태를
직접 스캔해서 아직 못 채운 행만 채우는 단일 백필 단계**로 통일했습니다
(`EnrichmentService.enrich_data`):

1. **이미 채워진 행 스킵**: `pd.notna(row.get("종가"))`면 API 재호출 없이 건너뜀 — 재실행이
   안전(idempotent)해짐.
2. **상장일 컷오프 스킵**: 상장일 15:50(장마감 후 KRX 시세 확정 대기 버퍼)이 아직 안
   지났으면 건너뜀. 다음 실행에서 자동으로 재시도됨 — "실패하면 끝"이 아니라 "아직
   때가 안 됐으면 다음 번에"로 바뀜.

`full`/`daily` 커맨드는 크롤링 직후 이 백필 단계를 자동 호출하고, 수동 `enrich` 커맨드는
동일 로직을 전체 DB 대상으로 재사용합니다 — 판단 기준이 완전히 하나로 통일됨.

**교훈:** "완료 여부" 판단 로직은 반드시 **DB를 직접 조회하는 단일 함수/서비스**로 통일하고,
자동 경로와 수동 경로가 같은 함수를 쓰게 만들 것. 시점(장마감 전/후) 판단이 필요한
도메인이면, "실패 시 포기"가 아니라 "조건이 안 맞으면 다음 실행에서 자동 재시도"로 설계할 것.

### 2.3 NaN 종목명이 스킵 조건을 통과하던 버그

`if not stock_name:`로 결측 종목명을 걸러내려 했는데, pandas가 결측 종목명을 `NaN`(float)로
로드하면 `bool(nan)`이 `True`라 이 조건을 통과했습니다. 조용히 넘어가던 게 아니라 그 다음
문자열 처리 단계에서 예외가 나고 넓은 `except Exception`에 삼켜져 "[SKIP]" 대신
"[ERROR]" 로그만 매번 찍혔습니다. `if pd.isna(stock_name) or not stock_name:`로 수정.

**교훈:** pandas DataFrame에서 온 값의 결측 체크는 `not x`가 아니라 `pd.isna(x)`(또는 둘 다)를
써야 함 — `bool(float('nan'))`은 `True`.

### 2.4 어댑터가 예외를 raise하는 설계 때문에 실제로 발생한 사고

Google Drive 연동(`GoogleDriveAdapter`)이 실패 시 예외를 그대로 raise하는 구조였고, 모든
호출부가 매번 `try/except`를 직접 감싸야 했습니다. Drive 동기화 유틸(`drive_sync.py`)에
새 호출(`get_or_create_subfolder("db")`)을 추가하면서 **이 한 곳만 try/except를
빠뜨렸고**, Drive 인증이 실패하면 크롤링과 가격 백필이 이미 성공했음에도 전체 커맨드가
예외로 실패 처리되는 버그가 실제로 발생했습니다(코드 리뷰 중 발견).

`krx-auto-crawling`의 `StoragePort`(모든 메서드가 `bool`/`Optional[...]`을 반환하고 어댑터
내부에서 예외를 직접 삼키는 계약)와 비교 검토한 뒤, 우리 `StoragePort`도 같은 방식으로
재설계했습니다: `upload_file() -> Optional[str]`, `list_files() -> list`(실패 시 빈 리스트),
`download_file() -> bool`. 호출자 실수(로컬 파일 없음)만 여전히 예외로 raise.

이 리팩터링 과정에서 **회귀를 하나 더 발견**했습니다: `auth.py`/`health.py`의 "Drive 연결
테스트"는 `list_files()`가 실패 시 raise하는 동작에 의존하고 있었는데, 반환값 기반으로
바꾸면 인증 실패가 "연결 확인됨(0개)"로 오탐될 뻔했습니다. 실패를 명확히 알아야 하는
호출자를 위해 `ensure_authenticated()`(실패 시 그대로 raise)를 별도로 노출해 해결.

**교훈:** "실패를 삼키고 안전한 값을 반환"하는 계약으로 인터페이스를 바꿀 때는, **그
실패 신호에 실제로 의존하고 있는 다른 호출부가 있는지 전수 조사**할 것 (`grep`으로
해당 메서드의 모든 호출부 확인). 헬스체크/연결테스트처럼 "실패 자체가 목적"인 호출은
예외 삼키기 계약에서 예외로 취급해야 함.

### 2.5 리팩터링 중 추가한 테스트가 실제로는 실행되지 않고 있었음

Google Drive 서브폴더 기능 추가 시 작성한 테스트 2개(`testget_or_create_subfolder_...`)가
`test` 뒤에 언더스코어를 빠뜨린 오타 때문에 pytest의 `python_functions = ["test_*"]` 패턴에
안 걸려 **한 번도 수집/실행되지 않고 있었습니다**. `--collect-only`로 실제 수집된 테스트
개수를 세어보다가 발견. 이름을 바로잡아 실제로 돌아가게 수정.

**교훈:** 테스트를 추가한 직후엔 `pytest -v --collect-only`(또는 실패를 일부러 주입해서
빨간불이 뜨는지)로 **그 테스트가 진짜로 수집/실행되는지 한 번은 직접 확인**할 것.
"통과했다"는 메시지만 보고 넘어가면 이런 오타가 영원히 안 잡힘.

### 2.7 원격 백업(Drive 업로드) 대상 범위를 "리포트 조회 기간"으로 좁혔다가 연도 경계에서 변경분을 놓칠 뻔함 (ceiling-tracker 마이그레이션에서 실제 발생)

`ceiling-tracker`는 리포트 생성(`export-excel --year <올해>`) 끝에 그 해의 `db/{year}.db`를 Drive에
백업하도록 만들었습니다. 처음엔 "리포트가 조회한 날짜 범위(`start_date.year`~`end_date.year`)에 속한
연도의 db만 올리면 된다"고 판단했는데, 이 프로젝트의 "완료 판단"(2.2절과 동일 계열) 로직상 **지난
연도의 코호트도 새해에 들어서까지 미완결 추적 중이면 여전히 업데이트**됩니다(예: 12월 말 코호트가
1월 초까지 가격을 채워 넣음 — 파일은 연도별로 분리돼 있으므로 이 업데이트는 지난 연도 db 파일에
기록됨). 데일리 크론은 항상 "올해"만 조회 범위로 넘기므로, 이 흐름대로면 **실제로 방금 바뀐 지난
연도 db가 백업 대상에서 누락**될 뻔했습니다 (사용자 리뷰로 발견, 아직 실제 유실 사고로 이어지기
전에 수정).

2.5절(SSOT 가이드)의 "연/월 경계는 실측 검증"이 *조회* 로직의 경계 문제였다면, 이건 같은 원인이
*아웃바운드 동기화 범위 결정*에도 그대로 적용된다는 확장 사례입니다. 고친 방법은 "리포트 날짜
범위"라는 대리 지표 대신, **db 디렉터리에 실제로 존재하는 파일 전체를 매번 업로드 대상으로 삼는
것**이었습니다 — 파일 개수/크기가 작으면 mtime 추적 없이 "전부 재업로드"가 가장 단순하고 안전한
선택입니다.

**교훈:**
> "무엇을 동기화할지"를 업무적 의미의 날짜 범위(리포트 기간 등)로 추론하지 말 것 — 실제로 어떤
> 저장 단위(연도별 파일 등)가 이번 실행에서 쓰기 작업을 받았는지가 기준이어야 함. 파일 수가 적다면
> "범위를 정확히 계산"하는 대신 "전체를 매번 다시 올리는" 쪽이 더 단순하고 경계 버그에 안전함.

### 2.8 자연키(종목코드 등)가 없는 레거시 데이터에서, 빈 문자열 동등 비교가 서로 다른 엔티티를 중복으로 오판함 (ceiling-tracker 마이그레이션에서 실제 발생)

`ceiling-tracker`가 이 문서를 참고해 Parquet → SQLite로 옮긴 뒤, 이어서 종목코드가 아예 없는
**레거시 엑셀(2020~2025년)** 데이터까지 SQLite로 마이그레이션했습니다. 이 레거시 데이터는 종목마다
`code=''`로 채워졌는데, 코호트에 종목을 추가하는 함수의 중복 체크가 `기존종목.code == 신규종목.code`를
code 유무와 무관하게 실행하고 있었습니다. `'' == ''`는 항상 참이므로, **같은 날짜(코호트) 안에서
종목코드가 없는 종목이 두 개 이상이면 첫 번째만 남고 나머지는 전부 "이미 있는 종목"으로 오판되어
조용히 버려졌습니다** — 예외도, 로그도 없이 데이터가 사라지는 조용한 데이터 유실이었음.

2.1절의 "PK에 정정 가능한 필드를 넣지 말라"와는 다른 종류의 함정입니다: 이번엔 SQL PK 설계 문제가
아니라, **애플리케이션 코드의 동등성 기반 dedup 로직이 "값이 비어있어서 우연히 같은" 경우를 진짜
동일 엔티티로 착각**한 것입니다. `pytest --collect-only`처럼 정적으로는 안 잡히고, 실제 데이터로
end-to-end 검증(엑셀 원본 행 수 vs DB 종목 수 비교)을 해봐야 드러났습니다.

**교훈:**
> 자연키(종목코드 등)가 선택적이거나 레거시 소스엔 아예 없는 도메인이면, "코드가 있으면 코드로,
> 없으면 이름으로" 같은 폴백 비교 로직을 짤 때 **두 대상 모두 코드가 비어있는 경우를 별도로
> 처리**할 것 — 단순히 `a.code == b.code or a.name == b.name`처럼 이어붙이면 빈 값끼리는 항상
> 같다고 나옵니다. 이런 마이그레이션 뒤에는 **소스와 이관 결과의 행 수/개체 수를 실제로 세어
> 비교**하는 검증을 반드시 한 번은 돌릴 것 — 조용히 사라지는 데이터는 카운트 비교 없이는 절대
> 안 드러납니다.

### 2.6 참고 프로젝트 패턴을 검증 없이 그대로 복사했다가 배포 중 발견한 문제

`krx-auto-crawling`의 `cron-entrypoint.sh`(env를 파일로 덤프한 뒤 cron 잡에서 다시
로드하는 패턴 — 그 프로젝트는 config가 OS 환경변수 주입에 의존하기 때문에 필요)를 그대로
복사해 왔는데, 실제로 컨테이너를 띄워 검증하는 과정에서 덤프된 env 파일에
`KRX_USERNAME`/`GOOGLE_DRIVE_FOLDER_ID`가 전혀 없다는 걸 발견했습니다. 원인은 이
프로젝트의 `config.py`가 `pydantic-settings`로 `/app/.env` 파일을 **직접** 읽어들이는
방식이라(OS 환경변수 주입 여부와 무관), cron 잡이 애초에 환경변수를 상속받을 필요가
없었던 것. 불필요한 코드를 제거.

**교훈:** 다른 프로젝트의 인프라 패턴(특히 "왜 이게 필요한지"가 코드만 봐서는 안 드러나는
워크어라운드)을 가져올 때는, **그 워크어라운드가 전제하는 조건이 우리 프로젝트에도
실제로 성립하는지** 반드시 확인할 것. 실제 배포 환경에서 한 번 실행해보고 검증하는 게
가장 빠른 확인 방법.

## 3. Docker 전환 시 문제와 원인

### 3.1 `print()`가 Docker 로그 순서를 뒤섞을 위험

`krx-auto-crawling`이 겪었던 문제(비-TTY 환경에서 `print()`의 내부 버퍼링과 `logging`의
별도 flush 타이밍이 어긋나 로그 순서가 실제 실행 순서와 다르게 보일 수 있음 — "중복
실행"으로 오인하기 쉬움)를 미리 반영해, Docker 전환 전에 `src/` 전체에서 남아있던
`print()` 19곳(파싱 전략/파서, `PlaywrightPageProvider`, `GoogleDriveAdapter`)을
`logger.info/warning/error`로 일괄 교체했습니다. `auth.py`의 Rich `console.print`는
사람과의 대화형 상호작용이 목적이라 대상에서 제외.

### 3.2 Windows 체크아웃 시 셸 스크립트가 CRLF로 깨질 위험

`docker/*.sh`, `docker/crontab`, `Dockerfile`을 새로 추가하면서 `git add` 시 "LF will be
replaced by CRLF" 경고를 확인했습니다. Windows에서 `core.autocrlf`가 켜져 있으면 다음
체크아웃 때 이 파일들이 CRLF로 변환되고, 리눅스 컨테이너 안에서 `#!/bin/sh\r`로 shebang이
깨져 `bad interpreter` 오류가 날 수 있습니다. `.gitattributes`에
`docker/*.sh text eol=lf`, `docker/crontab text eol=lf`, `Dockerfile text eol=lf`를
추가해 항상 LF로 체크아웃되도록 강제.

**교훈:** Windows에서 작업하며 리눅스 컨테이너에 직접 복사되는 셸 스크립트를 추가할
때는 `.gitattributes`로 줄바꿈을 강제할 것 — 로컬에서 빌드가 잘 됐다고 안심하면 안 됨
(로컬 워킹 디렉터리의 파일은 이미 LF일 수 있어도, 재체크아웃 시 깨질 수 있음).

### 3.3 cron 데몬 기동에 root 권한 필요 (krx와 동일 이유)

`krx-auto-crawling`과 동일하게, 컨테이너를 non-root(`nonroot`)로 돌리면 cron 데몬 기동과
`/proc/1/fd/1`(컨테이너 stdout) 리다이렉션에 필요한 권한이 없어 스케줄된 잡이 아예 실행되지
않습니다. `docker-compose.yml`에서 **`crawler-cron` 서비스만** `user: root`로 오버라이드
(1회성 실행용 `crawler` 서비스는 기본 `nonroot` 유지).

후속 조치: 이 root 권한이 cron 데몬 기동/`/proc/1/fd/1` 리다이렉션에만 필요하고
실제 크롤링(Playwright 브라우저/외부 HTTP 요청/Drive 업로드)에는 불필요하다는 걸
나중에 알아채고, `run-crawl.sh`에서 `su -s /bin/sh -c '...' nonroot`로 **실제 작업만**
nonroot로 내려 실행하도록 좁혔습니다. 리다이렉션은 root 셸이 이미 열어둔 파일
디스크립터를 `su`의 자식 프로세스가 그대로 상속하므로(권한 체크는 `open()` 시점에만
일어남) nonroot로 낮춰도 로그는 계속 정상적으로 써집니다. `docker run --user root ...`로
fd 상속 동작과, 마운트된 볼륨(`db/`, `output/`)에 nonroot가 실제로 쓸 수 있는지를
직접 검증한 뒤 적용.

**교훈:** "cron 데몬 기동에 root가 필요하다"가 "그 잡이 하는 모든 일에 root가
필요하다"를 의미하지 않음. root가 필요한 건 데몬 기동/fd 권한뿐이므로, 실제 페이로드는
`su`/`gosu`로 최대한 좁은 권한으로 실행할 것.

### 3.4 cron 잡이 Dockerfile의 `ENV PATH`를 상속받지 못함

실제 배포 후 로그에서 `run-crawl.sh: 4: crawler: not found`를 발견했습니다.
Dockerfile에서 `ENV PATH="/app/.venv/bin:$PATH"`로 가상환경을 PATH에 걸어뒀지만, 이는
**컨테이너 기동 시 최초 프로세스(그리고 그 자식들)**에만 적용되는 환경변수이고, cron
데몬이 그 이후 스폰하는 잡 프로세스는 이 PATH를 물려받지 않습니다(cron은 최소 PATH
`/usr/bin:/bin`으로 잡을 실행). `run-crawl.sh`에서 `crawler`를 절대경로
(`/app/.venv/bin/crawler`)로 호출하도록 수정해 해결.

**교훈:** Dockerfile의 `ENV`는 cron처럼 **자체적으로 새 환경을 구성해 잡을 스폰하는
데몬** 안에서는 상속되지 않을 수 있음. cron 잡 스크립트는 PATH에 의존하지 말고
절대경로로 실행할 것 — `docker build`만으로는 안 잡히고, 실제 스케줄이 발화되는 걸
봐야 발견됨(2.6/3.6과 같은 종류의 함정).

### 3.5 같은 원인이 su 권한 축소 이후 Playwright도 깨뜨림

3.3의 su 권한 축소를 적용한 뒤 실제 배포에서 `BrowserType.launch: Executable doesn't
exist at /home/nonroot/.cache/ms-playwright/...` 오류가 새로 발생했습니다. 원인은
3.4와 같은 뿌리: Dockerfile의 `ENV PLAYWRIGHT_BROWSERS_PATH=/ms-playwright`도 cron
잡 프로세스에 상속되지 않아, Playwright가 지정된 경로 대신 nonroot의 기본 캐시 경로
(`~/.cache/ms-playwright`)를 찾다 실패한 것. `run-crawl.sh`의 `su` 커맨드 문자열
안에 `PLAYWRIGHT_BROWSERS_PATH=/ms-playwright`를 직접 명시해 해결 — cron/su의 환경
상속 규칙을 이해하려 하기보다, 실제 실행되는 명령어 문자열에 필요한 값을 인라인으로
박아 넣는 쪽이 더 확실하고 디버깅하기 쉬웠습니다.

**교훈:** cron 잡 안에서 실행하는 프로세스가 (우리 앱 설정이 아니라) **서드파티
라이브러리가 직접 읽는 OS 환경변수**에 의존한다면, "우리 config는 .env를 직접
읽으니 env 상속이 필요 없다"는 판단이 그 라이브러리에는 적용되지 않음. Dockerfile에
`ENV`로 박아둔 값이라도 cron 잡 안에서 실제로 보이는지 배포 후 반드시 확인할 것 —
이번처럼 권한/PATH 문제를 하나 고치고 나면 그 다음 계층에서 같은 종류의 문제가 또
나올 수 있음.

### 3.6 실제 배포로 검증

`docker build` → `docker run`으로 이미지 빌드/CLI 동작을 먼저 확인하고, `docker compose up
-d crawler-cron`으로 실제 배포한 뒤:

- `docker exec ... ps aux | grep cron` — `cron -f`가 PID 1로 떠 있는지
- `docker exec ... cat /etc/cron.d/crawler-cron` — crontab 내용/권한(0644)이 맞는지
- `docker exec ... sh -c "cd /app && uv run python -c 'from config import config; ...'"` —
  `.env`가 실제로 로드되는지 (2.6절 문제를 이 단계에서 발견)

**교훈:** Docker 관련 변경은 로컬 `uv run` 테스트가 전부 통과해도 안심할 수 없음 —
**실제로 이미지를 빌드하고 컨테이너를 띄워서** 볼륨 마운트, 권한, 환경변수 로딩을 확인할
것.

### 3.7 docker-compose 프로젝트 이름 충돌로 다른 프로젝트 컨테이너가 삭제됨 (ceiling-tracker 마이그레이션에서 실제 발생)

`docker-compose.yml`을 `docker/` 폴더 안에 두는 구조(이 문서와 `krx-auto-crawling`이 공유하는
패턴)에서는, `name:`을 명시하지 않으면 Compose가 프로젝트 이름을 폴더명("docker")으로 추론합니다.
같은 구조를 쓰는 프로젝트가 여러 개면 전부 이름이 겹치고, 이 상태에서 `docker compose down
--remove-orphans`를 실행하면 **다른 프로젝트의 실행 중이던 컨테이너를 orphan으로 오인해
삭제**합니다. 실제로 `ceiling-tracker`를 이 패턴으로 옮기는 검증 도중, `krx-auto-crawling`의
상시 운영 중이던 크론 컨테이너가 이 문제로 삭제되는 사고가 있었습니다 (이미지가 남아있어 재기동으로
복구는 됐음).

**교훈:**
> `docker/` 서브폴더에 compose 파일을 두는 프로젝트는 전부 `docker-compose.yml` 최상단에
> `name: <프로젝트-고유이름>`을 명시할 것. `container_name:`만으로는 막지 못함 — orphan 판정
> 기준은 컨테이너 이름이 아니라 프로젝트 라벨이기 때문.

### 3.8 CLI 커맨드가 예외를 삼키고 exit code 0으로 끝나서 `set -e` 기반 실패 감지가 무력화됨

`daily_update`/`export_excel` 같은 CLI 커맨드가 내부에서 `try/except`로 예외를 잡아 에러 메시지만
출력하고 정상적으로 함수를 반환하고 있었습니다. 이 자체는 사람이 터미널에서 직접 실행할 땐 무해해
보이지만, **cron이 실행하는 셸 스크립트가 `set -e`로 "이전 단계 실패 시 다음 단계를 건너뛴다"를
구현하는 순간 조용히 깨집니다** — 프로세스가 항상 exit code 0으로 끝나니 셸은 "성공"으로 인식하고
다음 단계(리포트 생성, Drive 업로드 등)를 그대로 진행합니다. 크론 로그에는 에러 메시지가 찍혀
있는데도 파이프라인 전체는 "성공"으로 기록되는 상태.

**교훈:**
> cron/셸 스크립트가 `set -e` 또는 `if errorlevel 1`류의 종료 코드 체크로 파이프라인 단계를
> 제어한다면, **그 스크립트가 호출하는 모든 CLI 커맨드가 실패 시 실제로 0이 아닌 exit code로
> 끝나는지 하나씩 확인**할 것. `try/except`로 예외를 잡아 사람이 읽을 메시지를 출력하는 코드는
> 대부분 `sys.exit(1)`(또는 등가의 재-raise)을 빠뜨리기 쉬운 자리임. `click.testing.CliRunner`로
> "예외를 강제로 일으켰을 때 `result.exit_code != 0`인지"를 각 커맨드마다 회귀 테스트로 남겨둘 것.

## 4. 다른 크론잡을 같은 구조로 옮길 때 체크리스트

1. **PK에 정정 가능한 필드가 없는지 확인**: 시계열/이력 필드를 PK에 포함하면 정정 시
   중복 적재됨. 불변 식별자만으로 PK 구성.
2. **완료 판단 로직 단일화**: "이미 처리됨" 판단은 DB를 직접 조회하는 함수 하나로
   통일하고, 자동/수동 호출부가 같은 함수를 쓰게 만들 것. 시점 의존 로직이면 "실패=포기"가
   아니라 "다음 실행에서 자동 재시도"로 설계.
3. **pandas 결측치 체크는 `pd.isna()`**: `not x`만으로는 `NaN` float를 못 거름.
4. **어댑터의 실패 반환 계약을 통일**: 예외 raise 방식이면 모든 호출부가 try/except를
   빠뜨리지 않아야 하는 부담이 생김. 가능하면 어댑터 내부에서 실패를 삼키고
   `Optional`/`bool`/빈 컬렉션으로 반환하는 계약을 쓰되, 실패 자체가 신호여야 하는
   호출부(헬스체크 등)는 별도 메서드로 분리.
5. **인터페이스 계약을 바꿀 때는 실패 신호에 의존하는 다른 호출부를 전수 조사**:
   `grep`으로 해당 메서드의 모든 호출부를 확인하고, 그 신호에 의존하는 로직이 있는지 검토.
6. **신규 테스트는 수집/실행되는지 직접 확인**: `pytest --collect-only`로 이름 패턴이
   맞는지 확인하거나, 일부러 실패시켜 빨간불을 봐야 함.
7. **다른 프로젝트의 인프라 패턴을 가져올 때는 전제 조건을 검증**: 그 워크어라운드가
   왜 필요했는지 이해하고, 우리 프로젝트에도 같은 전제가 성립하는지 확인.
8. **`print()` 전량 제거**: Docker(비-TTY)로 옮기기 전에 로깅으로 통일.
9. **`.gitattributes`로 셸 스크립트 줄바꿈 강제**: Windows에서 작업하는 경우 특히 중요.
10. **cron 컨테이너 권한 확인**: non-root로 스케줄러 자체가 동작하는지 먼저 확인. 안 되면
    해당 서비스만 root로 오버라이드하고 나머지는 nonroot 유지.
11. **실제 이미지를 빌드/기동해서 검증**: 볼륨, 권한, 환경변수 로딩 방식(파일 직접 읽기
    vs OS 환경변수 주입)이 로컬 실행과 다를 수 있음.
12. **cron 잡 스크립트는 PATH에 의존하지 말 것**: Dockerfile의 `ENV PATH`는 cron이
    스폰하는 잡 프로세스에 상속되지 않음. 실행 파일은 절대경로로 호출.
13. **cron 데몬 기동에 root가 필요해도, 실제 작업까지 root로 돌리지 말 것**: 데몬
    기동/fd 권한에만 root가 필요하면 `su`/`gosu`로 실제 페이로드는 nonroot로 내릴 것
    (fd는 `open()` 시점에만 권한 체크되므로 root가 먼저 열어둔 리다이렉션은 자식이
    nonroot여도 그대로 상속됨).
14. **cron 잡이 실행하는 서드파티 라이브러리의 OS 환경변수 의존성도 확인할 것**:
    "우리 config는 .env를 직접 읽으니 env 상속 불필요"는 우리 앱 코드에만 해당함.
    Playwright의 `PLAYWRIGHT_BROWSERS_PATH`처럼 라이브러리가 OS 환경변수를 직접
    읽는 경우, Dockerfile `ENV`로 박아둬도 cron 잡엔 안 물려가므로 실행 커맨드에
    명시적으로 지정할 것.
15. **원격 백업 대상은 "실제로 쓰기 작업을 받은 저장 단위" 기준으로**: 업무적 날짜 범위(리포트
    조회 기간 등)로 백업 대상을 추론하면 연도/기간 경계에서 실제로 바뀐 파일이 누락될 수 있음
    (2.7절). 파일 수가 적다면 범위 계산 없이 전체를 매번 재업로드하는 쪽이 더 안전함.
16. **자연키가 없는 레거시 데이터의 dedup 로직 점검**: "코드 있으면 코드, 없으면 이름"류의
    폴백 동등 비교는 두 대상 모두 코드가 비어있을 때 항상 같다고 오판할 수 있음 (2.8절).
    마이그레이션 후 소스와 결과의 행 수/개체 수를 실제로 세어 비교할 것.
17. **`docker/` 서브폴더에 compose 파일을 두는 프로젝트는 `name:` 명시**: 안 그러면
    폴더명 기준으로 프로젝트 이름이 겹쳐서 `docker compose down --remove-orphans`가
    다른 프로젝트의 컨테이너를 삭제할 수 있음 (3.7절, 실제 사고 발생).
18. **cron이 호출하는 모든 CLI 커맨드의 실패 시 exit code 확인**: `try/except`로 예외를
    삼키고 메시지만 출력한 뒤 정상 반환하면, `set -e` 기반 파이프라인 제어가 무력화됨
    (3.8절). `CliRunner`로 실패 시 `exit_code != 0`을 회귀 테스트로 남길 것.

## 5. 오케스트레이션 레이어 정리 (부록)

DB SSOT 전환과 별개로, CLI 커맨드(`full_crawl.py`/`daily_update.py`) 안에 "수집 → 백필 →
변경 연도 계산" 로직이 그대로 나열돼 있어 순환복잡도가 높고(radon 기준 C등급) 유닛테스트도
어려웠습니다. `krx-auto-crawling`의 `DailyRoutineService`(오케스트레이션 로직을
`core/services`의 별도 서비스로 분리하고 CLI는 그 서비스를 호출만 하는 얇은 어댑터로 두는
패턴)를 참고해 `CrawlOrchestratorService`를 신설했습니다.

krx의 `execute()`는 `None`을 반환하고 서비스 내부에서 로깅까지 처리하는데, 우리는
`CrawlRunResult(collected_count, changed_years)` 값 객체를 반환하도록 설계했습니다 —
오케스트레이터는 순수 로직(호출 순서 조합)만 책임지고, 로그 문구는 CLI가 결정합니다.
`run_daily`의 "1월이면 전년도까지 백필" 판단 기준일도 `today` 파라미터로 주입 가능하게
해서, 실제로 1월이 아니어도 그 경계 로직을 유닛테스트할 수 있게 했습니다.

결과: `full_crawl()` C→A(5), `daily_update()` C→B(8) (radon cc 기준). 오케스트레이터
자체는 mock 기반 TDD로 호출 순서/changed_years 병합/1월 경계 케이스를 테스트.

**교훈:** 참고 프로젝트의 패턴을 그대로 베끼기보다, "왜 이 구조인가"를 이해한 뒤 우리
상황에 맞게 개선할 부분(로깅과 로직의 분리, 시간 의존 로직의 테스트 가능성)을 찾아
반영할 것.

## 6. weekly_gainers 포팅에서 드러난 이 프로젝트(new_stock_crawler) 자체의 실제 버그

같은 DB SSOT + Docker 패턴을 `weekly_gainers`에 포팅하면서(2026-08-14) 이 문서가 아직
다루지 않은 문제 두 가지를 발견했습니다. 포팅 대상 프로젝트뿐 아니라 **이
프로젝트(`new_stock_crawler`) 자체 코드에도 그대로 존재**하는 것으로 확인했습니다.
**2026-08-19에 둘 다 수정 완료**(`crawler-cron` 재빌드/재기동까지 반영, 아래 각 절에
수정 내용 기록).

### 6.1 ENV TZ=Asia/Seoul이 cron 잡에도, cron 데몬 스케줄링에도 반영 안 될 수 있음

`Dockerfile`을 보면 `apt-get install tzdata` 이후 `ENV TZ=Asia/Seoul`만 설정하고
`/etc/localtime` 심볼릭 링크는 갱신하지 않습니다. §3.4/3.5에서 이미 "Dockerfile의 ENV는
cron 잡 프로세스에 상속되지 않는다"를 PATH/PLAYWRIGHT_BROWSERS_PATH로 겪었는데, TZ에는
같은 체크리스트를 적용하지 않았습니다.

이번엔 datetime 값이 어긋나는 정도로 끝나지 않습니다 - **cron 데몬(crond) 자체가
crontab의 "50 15 * * 1-5" 같은 시각을 시스템 로컬타임(`/etc/localtime`) 기준으로
해석**하므로, `/etc/localtime`이 기본값(Etc/UTC)에 머물러 있다면 실제 발화 시각이 의도한
15:50 KST가 아니라 **15:50 UTC(= 다음날 새벽 00:50 KST)**일 수 있습니다. `docker exec ...
date`로 컨테이너 내부 시각이 실제로 KST인지 직접 확인하기 전까지는 겉보기 crontab 설정만
보고 안심하면 안 됩니다.

**수정 방법**: `RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ >
/etc/timezone`을 tzdata 설치 직후에 추가 - `TZ` 환경변수를 완전히 unset한 채로 `date`를
실행해도 KST가 나오는지로 검증할 것(env 상속 여부와 무관하게 OS 레벨에 고정되므로).

**수정 완료**(2026-08-19): 위 `RUN ln -snf ...` 라인을 `Dockerfile`에 추가하고,
`docker exec ... sh -c "unset TZ; date"`로 KST가 나오는 것까지 실측 검증함.

### 6.2 크롤링이 실패해도 last_crawl_date가 전진 — 갭 백필이 무력화될 수 있음

`crawl_orchestrator_service.py`의 `run_daily()`가 `self.crawler.run_scheduled(...)` 호출의
성공/실패와 무관하게 곧바로 `self.repository.set_last_crawl_date(target_date)`를
호출합니다. weekly_gainers 포팅 중 코드 리뷰에서 발견한 것과 동일한 형태의 문제로,
크롤링이 며칠간 실패해도(예: KRX/사이트 접속 장애) `last_crawl_date`는 계속 "오늘"로
갱신되어, 다음 성공한 실행에서 공백이 실제보다 작게 보여 정작 실패했던 구간이 백필
대상에서 빠집니다.

**수정 방향**: `run_scheduled`가(또는 그 호출부가) 실제 수집 성공 여부를 반환하도록 하고,
성공했을 때만 `set_last_crawl_date`를 호출할 것.

**수정 완료**(2026-08-19): `DetailScraperAdapter.scrape_details`가 (성공 목록, 실패
종목명 목록) 튜플을 반환하도록 바꾸고, `run_scheduled()`는 실패 종목이 하나라도 있으면
`PartialScrapeFailureError`(성공분은 `partial_data`에 담아 전달)를 발생시키도록 함.
`run_daily()`는 이 예외를 잡아 partial_data로 계속 진행하되 `set_last_crawl_date`는
호출하지 않음 - 실패했던 구간은 다음 실행에서 자동 재시도됨. 재시도 정책(날짜 전체
보류 vs 실패 종목만 별도 기록)은 두 가지 선택지 중 "날짜 전체 보류"를 프로젝트
운영자가 선택해 반영함 - 전체 재수집은 종목명 upsert라 안전하다는 기존 전제(주석)를
그대로 활용.

## 7. 아직 다루지 않은 것 (의도적으로 미룬 항목)

- **GitHub Actions 등 외부 트리거 경로**: `daily_update.py`가 한때 "GitHub Actions용"으로
  설계됐었지만, 최종적으로는 krx와 동일하게 컨테이너 내장 cron으로 자체 호스팅하는
  방식을 채택. 외부 스케줄러 연동은 미검증/미착수.
- **Google Drive 동시 쓰기에 대한 파일 락**: 지금은 순차 실행이라 불필요, 병렬 실행 잡이
  생기면 재검토 (krx와 동일한 판단).
- **여러 크론잡의 실행 결과를 한곳에 모아 알림으로 전달하는 오케스트레이션**: 별도 논의
  필요, healthchecks.io류 cron 모니터링 서비스에 잡별 ping을 붙이는 방식을 권장.
- **`export_excel.py`/`enrich_data.py` 등 CLI 커맨드 함수 자체의 유닛테스트**: 오케스트레이션
  로직은 `CrawlOrchestratorService`로 분리해 테스트 가능해졌지만, typer 커맨드 함수
  자체(인자 파싱, 옵션 조합)는 여전히 테스트가 없음.
